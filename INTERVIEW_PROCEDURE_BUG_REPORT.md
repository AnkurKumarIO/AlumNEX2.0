# Interview Procedure & Notification System Bug Report

This report outlines the critical bugs identified in the interview request, slot booking, and notification workflow of the AlumNex platform.

## 1. Executive Summary
The primary issues stem from a mismatch between the database schema and the real-time notification logic, inconsistent notification type naming, and a partial implementation of "Instant Meet" functionality that bypasses the centralized notification system.

## 2. Identified Bugs

### Bug A: Missing Database Persistence for Meeting Links
- **Symptoms:** Students receive a "Join Now" notification via socket while online, but if they refresh the page or log in later, the notification in their history is missing the "Join Now" button or has a broken link.
- **Root Cause:** The `Notification` model in `prisma/schema.prisma` lacks a `room_id` column. While the backend emits the `room_id` via Socket.io, it cannot save it to the database.
- **Impact:** Critical. Prevents asynchronous joining of interviews if the initial socket event is missed.

### Bug B: Inconsistent Notification Types
- **Symptoms:** Notifications sometimes fail to render the correct icon or action button in the student dashboard.
- **Root Cause:** The backend uses `SLOT_BOOKED` and `SLOT_BOOKED_ALUMNI`, but the frontend `Dashboard.jsx` and `useNotifications.js` have partial or inconsistent mapping for these types.
- **Impact:** Medium. Leads to confusing UI states where a scheduled interview looks like a generic notification.

### Bug C: Instant Meet "Live" Notification Bypass
- **Symptoms:** Students are not notified when an Alumni starts an "Instant Meet" unless they happen to be on the exact same browser/tab where the action was initiated.
- **Root Cause:** `AlumniDashboard.jsx` attempts to push a `live` notification directly to `localStorage` (which is local to the Alumni's machine) instead of calling the backend API to notify the Student.
- **Impact:** High. The "Instant Meet" feature is essentially non-functional for the student side.

### Bug D: Authentication Context Mismatch
- **Symptoms:** Feedback submission fails or attributes ratings to the wrong user.
- **Root Cause:** `GoogleMeetInterviewRoom.jsx` attempts to read user data from `sessionStorage`, but the primary `AuthContext` and login flow use `localStorage`.
- **Impact:** Medium. Corrupts session history and analytics data.

### Bug E: TNP Coordinator Notification Failure
- **Symptoms:** TNP coordinators do not see "who both are having a meet" in their activity feed.
- **Root Cause:** The backend uses a hardcoded fallback ID (`tnp-001`) if it can't find a user with the role `TNP`. Additionally, the TNP notification logic is only triggered on `SLOT_BOOKED`, not on "Instant Meet" starts.
- **Impact:** Low/Medium. Hinders administrative oversight.

## 3. Corrective Procedure

### Step 1: Database Schema Update
- Add `room_id` (String?) to the `Notification` model in `prisma/schema.prisma`.
- Run `npx prisma generate` and `npx prisma migrate dev`.

### Step 2: Backend Route Refactoring
- Update `backend/routes/requests.js` to save `room_id` when creating notifications for `SLOT_BOOKED` and `ACCEPTED` statuses.
- Update the POST `/requests` and PATCH `/requests/:id` handlers to support a new `LIVE` notification type for instant meetings.
- Ensure the TNP coordinator notification logic fetches the correct user ID dynamically.

### Step 3: Frontend Notification Logic Sync
- Update `frontend/src/hooks/useNotifications.js` to correctly normalize and expose the `room_id` from the database.
- Update `frontend/src/pages/Dashboard.jsx` to handle the `LIVE` notification type and render the red "Join Now" button with the correct room link.

### Step 4: Alumni Dashboard Fix (Instant Meet)
- Modify `handleInstantMeet` in `AlumniDashboard.jsx` to call `api.updateRequest` with a specific flag or status that triggers a `LIVE` database notification to the student.
- Remove the `localStorage` notification hack.

### Step 5: Interview Room Auth Cleanup
- Standardize `GoogleMeetInterviewRoom.jsx` to use `localStorage` and `AuthContext` exclusively, removing references to `sessionStorage` for user identity.
